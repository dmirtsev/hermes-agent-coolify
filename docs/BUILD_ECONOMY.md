# Экономная проверка Hermes wrapper

Общая политика: [рабочая версия в tp-architecture](https://github.com/dmirtsev/tp-architecture/blob/codex/local-stand-20261019/docs/BUILD_AND_CANDIDATE_POLICY.md).
Она не принята в `main`, не меняет существующие workflow и не разрешает выпуск.

## Локальные проверки без модели и сети

Контрактные тесты используют локальные фикстуры и временные каталоги:

```sh
python3 -m unittest discover -s tests -p 'test_*.py'
```

Для shell-обвязок доступна проверка синтаксиса:

```sh
for file in *.sh; do sh -n "$file"; done
```

Проверка манифеста и fixture-smoke не обращается к реальным endpoint, если
передан `--fixture-dir`; она уже входит в контрактные тесты.

## Сохранённые обязательства

Для каждого из `economy`, `balanced`, `strong` сохраняются отдельные runtime,
том, ключи и фиксированная модель. Фактическое `config.yaml` и health evidence
должны подтверждать tier, commit, модель и token cap. Нельзя подменять это
полем `model` в запросе. Release evidence, авторизация и accounting contract
остаются обязательными по действующим документам.

Legacy Hermes runtime имеет иной подтверждённый commit и служит только для
совместимости; его нельзя использовать как базу merge для трёх профилей.

## Экономный порядок и пределы

Сначала запускать контрактные тесты и shell syntax. Docker-сборку wrapper и
реальные health/MCP-smoke выполнять для законченного блока, который затрагивает
контейнер или интеграцию. E2E с LLM — отдельная явно разрешённая проверка,
поскольку использует provider и может иметь стоимость.

В репозитории нет доказанных замеров стадий Dockerfile, кеша и порядка CI;
их нужно снять отдельным аудитом. Нельзя переносить локальную схему Cabinet
или считать её применимой к серверным профилям без такого измерения.

Готовый образ выбирается только при совпадении исходного SHA, платформы,
закреплённого upstream digest, build-аргументов и обязательных проверок.
Тег образа сам по себе не является доказательством готовности.
